# 哪些傳球失誤會直接導致失球？
### 用 Wyscout 事件資料偵測「致命的丟失球權」

> NYCU Data Mining HW2（Anomaly Detection）
> 狀態：**主實驗、消融、誤差分析、穩健性檢查完成**（2026-11-07，Tier 2 主方法改為驗證集選出的單邊版本）。所有結果可以用 `bash run_all.sh` 在一般電腦上約 18–20 分鐘重現
> 資料類別：**Tabular**（作業 5 類中的第 2 類），一筆資料 = 一次傳球失誤
> 姊妹專案：`hw2_foul_card`（犯規 → 吃牌）。兩者用同一份原始資料、同一種切分與評估協定

---

## 一句話說明

只用「傳球失誤當下就知道的資訊」（在哪裡丟、球落在哪裡、是否回傳、是否在對手壓迫下），判斷**這次失誤會不會在 15 秒內導致失球**。資料是表格型（一次失誤一列）。只用「沒有導致失球的失誤」訓練的 Isolation Forest，如果像一般做法一樣不分方向（雙邊），只能和最好的單一特徵（球的落點）打平；把每個特徵的危險方向寫進分數（單邊，由驗證集選出）後，PR-AUC 從 0.0102 顯著提高到 0.0173，前 1% 抓到的次數翻倍。監督式 XGBoost 仍然最好（0.0302），但和單邊版本的差距在 bootstrap 下不顯著。漏掉的致命失誤多半要經過 5–6 個對手動作才失球，從失誤當下看不出來。

## 1. 為什麼做這題

| 項目 | 內容 |
|---|---|
| **使用者** | 球隊的影片分析師、教練 |
| **決策** | 一場比賽約 146 次傳球失誤，平均只有約 0.45 次直接導致失球。賽後檢討時先看哪幾次？ |
| **警示之後的動作** | 把失誤排進檢討片段，找出「在哪種情況下出錯最致命」，用於訓練 |
| **審查預算** | 前 1% 與前 10% 的失誤（§5.4） |

**研究問題：**
> 只用「沒有造成失球的失誤」學出正常樣貌，能不能把致命的失誤當成異常抓出來？和犯規題目相比，結果有什麼不同？

**異常的定義（看結果之前就固定）：** 一次不準確的傳球（`Pass` 且帶 tag 1802），之後 15 秒內、同一個半場，對手進球（射門或自由球帶 tag 101，或我方烏龍球 tag 102）。

| | 例子（定義上的樣貌） |
|---|---|
| **正常** | 在對方禁區前傳中，被後衛解圍，對手往前推進，但沒有進球 |
| **異常** | 在自家禁區前被逼著回傳出錯，對手搶到球後 15 秒內進球 |

## 2. 資料

**Wyscout 公開事件資料**（Pappalardo et al. 2019，figshare），和犯規題目相同：

| 檔案 | 內容 | 用途 |
|---|---|---|
| `events_*.zip` | 3,251,294 個事件 | 傳球失誤、進球、前 10 秒情境 |
| `matches_*.json` | 1,941 場的日期、主客場 | 切分、主客場 |
| `players.json` | 3,603 名球員的位置 | 傳球者角色 |

- 賽事：英、法、德、義、西 2017/18 頂級聯賽，2016 歐洲盃，2018 世界盃
- 期間：2016-06-10 到 2018-07-15

### 2.1 一筆資料與標籤

| 項目 | 定義 |
|---|---|
| **一筆資料** | 一次 `Pass` 且帶 tag 1802（不準確）的事件，共 284,019 次 |
| **標籤** | 之後 15 秒內、同一個半場，對手進球 → 1 |
| **預測時間點** | 傳球的當下 |
| **不算丟球權** | 對抗（`Duel`）失敗。Wyscout 的對抗兩邊各記一筆，防守方被過掉也會記成「對抗失敗」，那不是丟球權 |
| **不能用** | 傳球之後的任何事件（落點補值是唯一例外，見 §2.3）；tag 2001（`dangerous_ball_lost`），標註員可能看完後續才標 |

**15 秒這個時間窗的影響**（探索階段的計數，包含對抗失敗，僅供參考）：10 秒 3,958 次、15 秒 4,976 次、30 秒 7,013 次。只算傳球失誤時，15 秒內有 869 次。

**tag 2001 不適合當標籤**：資料中有 4,028 次事件帶「危險的丟失球權」tag；其中同時是傳球失誤或對抗失敗、而且之後 15 秒內失球的，只有 299 次（其他事件類型沒有檢查）。標註員認為「危險」的丟球，大多沒有導致失球。

### 2.2 類別不平衡

| 切分 | 場次 | 失誤 | 15 秒內失球 | 比例 |
|---|---|---|---|---|
| 訓練 | 1,164 | 170,396 | 501 | 0.29% |
| 驗證 | 388 | 59,351 | 186 | 0.31% |
| 測試 | 389 | 54,272 | **182** | **0.34%** |
| 合計 | 1,941 | 284,019 | 869 | 0.31%（約 1 : 330） |

不平衡程度和信用卡詐騙相當。「全部判正常」的 accuracy 是 99.66%，所以 accuracy 不能當指標。

5,223 個進球中，有 812 個在進球前 15 秒內有對手的傳球失誤；869 次失誤對應這 812 個進球（少數進球前有多次失誤）。

### 2.3 落點缺值的修正

**問題：** 8,380 次失誤（3.0%）的傳球落點記為 **(0, 0)**，也就是剛好在我方球門線的角落。檢查原始事件後發現這是 Wyscout 沒有記錄落點時的佔位值：

| 檢查項目（世界盃 + 英超，2,016 次落點 x = 0） | 結果 |
|---|---|
| 落點剛好是 (0, 0) | 97% |
| 傳球種類 | 85% 是傳中 |
| 傳球起點 | 中位數 x = 89，91% 在對方半場 |
| 下一個事件 | 96% 是對手，多半是對手在他們自己的禁區觸球（例如 x = 4–13）或守門員出擊 |

也就是說，這些多半是**在對方禁區前傳中失敗**，球被解圍或被守門員接走，而不是傳到自家底線。

**修正（`fix_end`）：** 落點為 (0, 0) 時，用**之後第一個有真實座標的事件**補回（同一個半場、相隔不超過 5 秒）：
- 跳過沒有座標的事件、比賽中斷（`Interruption`），以及座標是**四個角落佔位值**（x、y 都是 0 或 100）的事件
- 找到的事件是對手的：座標換回我方視角 (100 − x, 100 − y)，共 6,164 次
- 找到的事件是本隊的：直接用，共 278 次
- 找不到：用傳球起點代替，共 1,938 次

補值後的落點 x 中位數是 91，符合「在對方禁區前丟球」。七個賽事都有這個問題（每個聯賽約 1,150–1,750 次），修正規則一致套用。

**第二版修正（誤差分析發現的）：** 第一版只看「下一個事件」。但傳中被守門員接走時，下一個事件常是「守門員出擊」或「撲救」，Wyscout 把它們的座標記成角落佔位值 (100, 100)；換回我方視角後落點又變成 (0, 0) 附近，等於把傳中又放回自家底線。英超裡，(0, 0) 傳中的下一個對手事件有 337 次是「守門員出擊」、41 次是「撲救」，座標全是角落。誤差分析（§6.5）時發現：單一特徵的測試集前 1% 裡有 341 次在對方三分之一丟球，其中 334 次就是這種補錯的傳中，全部沒有失球。第二版改成跳過佔位座標往後找，影響 1,847 次失誤（標籤不變）。

**例外說明：** 補值用到了傳球之後的事件，但只取它的**位置**來補回「這次傳球本身的落點」，這個資訊原本就屬於傳球事件，只是沒被記錄。其他特徵都不使用之後的事件。

**影響：** 補值的失誤失球率只有 0.05%（全體 0.31%）。沒有修正時，它們被當成「球掉到自家球門前」，排在單一特徵的最前面；`end_x`、`end_lateral`、`pass_len`、`backward` 都受到影響（三個版本的比較見 §6.1）。

## 3. 特徵（28 個）

全部只用傳球當下或之前的資訊。比分、本隊累計失誤數都在記錄後才更新。

| 組 | 特徵 | 意思 |
|---|---|---|
| **原始（19 個）** | `x`、`lateral` | 丟球位置；x = 0 是自家球門，`lateral` = \|y − 50\| |
| | `end_x`、`end_lateral`、`pass_len` | 球落在哪裡、傳球長度（公尺，以 105 × 68 換算）；落點已修正（§2.3） |
| | `backward` | 落點比起點更靠近自家球門 |
| | `pt_*`（7 個） | 傳球種類：一般、高球、大腳、傳中、頭球、穿透、手拋 |
| | `minute`、`home` | 比賽分鐘、是否主場 |
| | `role_DF/MD/FW/GK` | 傳球者位置 |
| **情境（9 個）** | `dist_own_goal`、`in_own_third` | 丟球點到自家球門距離、是否在自家三分之一 |
| | `counter_attack` | 這次傳球帶有反擊 tag |
| | `score_diff`、`team_prev_losses` | 當下比分差、本隊本場之前失誤幾次 |
| | `own_events_10s`、`opp_events_10s` | 前 10 秒兩隊的動作數 |
| | `opp_duel_3s` | 前 3 秒內對手有對抗（壓迫的近似） |
| | `own_min_x_10s` | 本隊前 10 秒最靠近自家球門的位置 |

**危險特徵組（6 個，事先依足球常識定義，不看標籤）：** `dist_own_goal`、`lateral`、`end_x`、`end_lateral`、`backward`、`opp_duel_3s`。也就是在哪裡丟、球丟到哪裡、是不是回傳、是否在壓迫下。

## 4. 探索分析（只用訓練場次）

**依丟球位置：**

| 區域 | 失誤數 | 佔全部失誤 | 15 秒內失球率 |
|---|---|---|---|
| 自家三分之一 | 48,526 | 28.5% | **0.54%** |
| 中場三分之一 | 63,658 | 37.4% | 0.27% |
| 對方三分之一 | 58,212 | 34.2% | 0.11% |

自家三分之一的失誤，失球率是對方三分之一的 4.8 倍；但它佔了 28.5%，一點都不罕見。

**單一特徵可分性**（訓練集）：

| 特徵 | 方向化 AUC | KS | 致命失誤平均 | 一般失誤平均 |
|---|---|---|---|---|
| `end_x` | 0.769 | 0.402 | 43.9 | 66.9 |
| `dist_own_goal` | 0.679 | 0.261 | 43.8 | 59.5 |
| `x` | 0.670 | 0.253 | 37.5 | 52.3 |
| `own_min_x_10s` | 0.622 | 0.205 | 30.9 | 39.8 |
| `in_own_third` | 0.618 | 0.237 | 52.1% | 28.4% |
| `pass_len` | 0.610 | 0.202 | 17.4 | 24.1 |
| `pt_simple_pass` | 0.607 | 0.214 | 59.9% | 38.4% |
| `score_diff` | 0.605 | 0.189 | −0.49 | −0.04 |

- **球落在哪裡比在哪裡丟更重要**：`end_x` 的 AUC 0.769，最高（修正落點前是 0.747）。
- **致命失誤的傳球比較短**（17.4 對 24.1 公尺），多是一般短傳（59.9% 對 38.4%），符合「在自家半場被逼著短傳出錯」。
- **回傳的失球率是其他方向的兩倍多**（0.54% 對 0.25%）。

圖 `results/figures/fig1_eda_train.png`：訓練集中正常與致命失誤的 `end_x`、`dist_own_goal` 分布，以及回傳與否的失球率。

**探索階段的假設**（在 §6 檢驗）：
- **H1**：致命失誤集中在「球往自家球門方向掉」的一側（落點低、回傳）。
- **H2**：危險只在單一方向：在對方禁區前丟球雖然也可能罕見，但不危險。所以只看罕見度、不分方向的雙邊分數會被安全方向的罕見值干擾。
- **H3**：失誤當下的資訊只能解釋一小部分；要等之後好幾次傳遞才進球的失誤，從當下很難看出來。
- **落後時比較容易失誤後失球**（平均比分差 −0.49），可能是落後的球隊壓上、身後空檔較大。

## 5. 方法與實驗設計

### 5.1 三層方法

| 層 | 方法 | 用到的標籤 |
|---|---|---|
| **Tier 1** | (a) 全部判正常；(b) 隨機分數；(c) 單一特徵：訓練集方向化 AUC 最高的 `end_x`（越小分數越高） | (c) 只用訓練集選特徵 |
| **Tier 2（主方法）** | Isolation Forest，只用訓練集**沒有導致失球**的失誤（169,895 次）訓練；`StandardScaler` 也只在這些資料上 fit。分數 s(x) = −`score_samples`(x)，越大越異常。驗證集從三個候選中選：全部 28 個特徵雙邊、危險 6 個雙邊、危險 6 個**單邊**。單邊：標準化後乘上事先決定的危險方向 `DANGER_SIGN`，安全方向的偏離壓成 0 | 訓練：不用；候選、超參數、τ：驗證集；方向不用標籤 |
| **Tier 2 參考** | Mahalanobis 距離（危險特徵組，雙邊） | 同上 |
| **Tier 3** | XGBoost 監督式分類，28 個特徵 | 訓練集標籤 |

### 5.2 切分與防止洩漏

| 項目 | 設定 |
|---|---|
| **切分** | 依比賽日期排序：前 60% 場次訓練（到 2018-02-03）、接著 20% 驗證（到 2018-04-07）、最後 20% 測試。和犯規題目完全相同的場次切分 |
| **三層共用** | 同一份切分、同一組指標、同一批測試失誤 |
| **驗證集** | 只用來選特徵組、超參數和 τ |
| **測試集** | 最後只評估一次 |
| **落點補值** | 規則固定（§2.3），所有切分一致套用，不用標籤 |

### 5.3 超參數（只用驗證集 PR-AUC 選）

| 方法 | 搜尋範圍 | 選出 |
|---|---|---|
| Isolation Forest | 候選 {全部 28 個雙邊, 危險 6 個雙邊, 危險 6 個單邊} × 樹數 {200, 500} × ψ {256, 1024, 4096} × max_features {0.5, 1.0}，共 36 組 | **危險 6 個、單邊**、500 棵、ψ = 256、max_features = 0.5（驗證 PR-AUC 0.0131；危險 6 個雙邊 0.0076；全部 28 個 0.0053） |
| XGBoost | max_depth {3, 5} × min_child_weight {1, 10}；learning rate 0.05，早停 100 輪 | depth 3、min_child_weight 10、153 棵樹（Windows；Linux 為 128 棵） |

**來源說明（誠實揭露）**：第一版只搜尋雙邊的候選。單邊的想法來自第一版主方法在**測試集**上的警示樣貌（標記了很多「罕見但安全」的失誤），所以加入這個候選時受到測試集的影響。之後重新跑完整的驗證集選擇，選出的是單邊（搜尋時 seed 0 的驗證 PR-AUC 0.0131；5 個 seed 平均 0.0128，見 §6.3）。同樣的現象只看驗證集也看得到：雙邊在驗證集前 1% 的 594 次警示中，有 108 次落在對方三分之一、全部沒失球（單邊只有 7 次；`results/ablation_log.json` 的 `validation_top1_by_zone`）。公開資料沒有其他賽季可以當全新的測試集，所以我們把測試集上的進步視為部分探索性的結果，另外用完全不含測試期的 leave-one-league-out 確認（§6.4 R5）。

**單一特徵基線是「監督式啟發法」**：特徵和方向都用訓練集標籤挑，是刻意保留的強基線。不用標籤、依常識挑的規則（−離自家球門距離）只有 0.0058。單邊的 6 個方向和訓練集資料呈現的方向 6/6 一致，所以用標籤學方向不會改變結果，只會讓 Tier 2 變成監督式。

### 5.4 指標

| 指標 | 為什麼 |
|---|---|
| **PR-AUC**（主指標） | 隨機猜的基準是異常比例（測試集 0.0034） |
| **前 1% / 前 10% 抓到幾次** | 對應「檢討時只看 1% 或 10% 的失誤」；測試集的 1% 是 543 次、10% 是 5,427 次 |
| ROC-AUC | 輔助 |

每個方法 5 個 seed（0–4），報告平均 ± 標準差。

**顯著性：兩種差距要分清楚**
- **逐 seed 差距**：主表「5 個 seed 各自 PR-AUC 的平均」相減，用 5 個 seed 的配對 t 檢定（單一特徵是確定性的，用單樣本 t 檢定）。只反映模型的隨機性。
- **集成差距**：先把 5 個 seed 的分數平均，再算 PR-AUC 相減，用**以比賽為單位的 block bootstrap**（1,000 次）算 95% CI。同時反映測試樣本的不確定性，**是我們判斷顯著與否的標準**。
- 平均 5 個 seed 的分數會讓單邊 Isolation Forest 的 PR-AUC 從 0.0173 升到 0.0186，所以兩種差距的數字不同（例如單邊 − 雙邊：逐 seed +0.0071、集成 +0.0087）。

## 6. 結果

### 6.0 各層實際用到的樣本數

三層從**同一份原始切分**出發（依比賽日期：1,164 / 388 / 389 場），在**同一個驗證集**上調參數與 τ、在**同一個測試集**上評估。差別只在訓練時用了哪些訓練樣本：

| 層 | 方法 | 訓練：正常 | 訓練：異常（致命） | 說明 |
|---|---|---|---|---|
| Tier 1 | 全部判正常、隨機分數 | 0 | 0 | 不需要訓練 |
| Tier 1 | 單一特徵（`end_x`） | 169,895 | 501 | 只用訓練集的標籤挑特徵與方向，沒有學參數 |
| Tier 2 | Isolation Forest（三個候選） | 169,895 | **0** | Normal-only：從訓練切分濾掉所有致命失誤；`StandardScaler` 也只在這些資料上 fit |
| Tier 2 參考 | Mahalanobis（危險 6 個） | 169,895 | **0** | 同上 |
| Tier 3 | XGBoost | 169,895 | 501 | 監督式，保留同一份訓練切分裡的異常樣本 |
| — | 驗證集（選特徵組、超參數、早停、τ） | 59,165 | 186 | 所有方法共用 |
| — | 測試集（只評估一次） | 54,090 | 182 | 所有方法共用 |

- **R4 可部署的修正（針對延遲的失球）**：傳球當下就知道的情境（反擊、前 10 秒雙方動作數、本隊最後防線）可以部署。XGBoost 從只用危險 6 個特徵改成全部 28 個，延遲失球在前 1% 從 4 次升到 9 次（前 10% 從 51 升到 59），快速失球不變（20 次）。單邊 Isolation Forest 要用這些特徵，得先替它們定義危險方向，留待之後。

- **R6 沒碰過的賽季（`src/statsbomb_external.py`）**：把鎖定的流程（Wyscout 上訓練好的 scaler、森林、XGBoost 和 τ，完全不重新訓練、不調參）套到 StatsBomb Open Data 的英超 2015/16（380 場、73,830 次失誤、151 次致命），整個研究過程都沒看過這份資料。**方向的效果重現了**：單邊顯著勝過雙邊（集成差距 +0.0020，CI [+0.0014, +0.0034]），雙邊前 1% 的 738 次警示中有 211 次落在對方三分之一、全部沒失球（單邊 6 次）。但單邊只和單一特徵打平（−0.0010，CI [−0.0022, +0.0009]），XGBoost 最穩。兩家資料的定義不同：致命失誤中回傳佔 19%（Wyscout 34%）、對抗佔 16%（26%），正好削弱了單邊最依賴的特徵。結果在 `results/external_statsbomb.csv`、`external_log.json`。

**模型學到什麼**（`results/feature_importance.csv`、`results/figures/fig4_feature_contributions.png`）：
- **XGBoost（TreeSHAP，xgboost 內建的 `pred_contribs`，5 個 seed 平均）**：`end_x` 最重要（mean |SHAP| 0.97，越小越容易失球），其次是比分差（0.35，落後時比較容易失球）和 `end_lateral`（0.28，越靠中路越危險）。
- **Isolation Forest（遮蔽法：把一個特徵換成正常訓練樣本的中位數，看分數掉多少）**：被標記的前 1% 中，`end_x` 最重要（0.056），其次是回傳、`lateral`、`dist_own_goal`（0.032–0.035）。案例 1 六個特徵的遮蔽貢獻都是正的，分析師看得到「正中路、離球門近、回傳、在壓迫下」這種能直接拿來檢討的解釋。
- **解釋的一致性（信任度的替代指標）**：582 次警示中，Isolation Forest 遮蔽貢獻最大的特徵，和 XGBoost 在危險 6 個特徵中 SHAP 最大的特徵一致的比例約 60%（大多是 `end_x`）。和教練實際審查決定的比對留待之後。
- 選遮蔽法而不是 SHAP 套件：SHAP 對 Isolation Forest 的解釋是「對路徑長度的貢獻」，需要額外安裝 `shap`（會連帶需要 numba，版本和 numpy 2.5 不一定相容）；遮蔽法直接回答「這個特徵如果是正常值，分數會掉多少」，在只有 6 個特徵時也容易驗證。

**審查預算與成本**：每隊每場約 73 次失誤，前 1% 約 1 段片段、前 10% 約 7 段；每段約 1 分鐘，等於每場 1 或 7 分鐘。從 1% 放寬到 10%，主方法每多找到 1 次致命失誤要多看約 95 段片段（(5,427 − 543) ÷ (68.0 − 16.6)），所以只有當「漏掉一個致命模式」的代價超過約 95 分鐘的審查時間，10% 才划算。錯過的代價無法量化、Isolation Forest 的分數也不是機率，所以用固定審查量（預算）決定 τ，而不是成本最佳化。

**15 秒的依據**：15 秒內的失球有 97% 發生在 10 個動作以內，和 VAEP 的 10 個動作視窗一致。

**實際影響**：摘要的「每場約 146 次失誤、0.45 次致命」是一場比賽兩隊合計；換成每隊每季（38 場）約 2,780 次失誤、8.5 次致命。檢討前 1%（28 段片段）平均可以找到 0.8 次致命失誤（主方法）、0.4 次（雙邊）、1.4 次（XGBoost）、0.1 次（隨機）；放寬到 10%（278 段），主方法可以找到 3.2 次。改用射門標籤時，同樣 28 段裡約有 6 段讓對手射門。

## 7. 結論與限制

**結論：**
1. **「罕見」是否等於「危險」取決於方向。** 不分方向的雙邊 Isolation Forest 只能和單一特徵打平；把事先決定的危險方向寫進分數（由驗證集選出），PR-AUC 提高 70%，前 1% 抓到的次數翻倍。影響最大的決定是分數的方向，不是模型種類（Mahalanobis、kNN、GMM 都沒有幫助）。
2. **監督式仍然較好，但差距不確定。** XGBoost 0.0302，和主方法的差距在 5 個 seed 上一致，但在 bootstrap 下不顯著。
3. **落點補值沒有洩漏。** 改成只用傳球當下的資訊，所有結果不變。
4. **剩下的風險多半發生在失誤之後。** 漏掉的致命失誤平均 5.9 個事件後才失球；加入失誤後 5 秒的發展就能抓回一部分。被標記但沒失球的失誤，有 20% 讓對手射門。
5. **normal-only 在這題不是效果來源**：致命失誤只佔 0.29%，混進訓練資料也幾乎沒有影響。

**部署與漂移：** 每季（或換教練後）用最新的正常失誤重新 fit scaler 和森林；固定 τ 時每週監看警示比例（預期 1%）和警示中自家三分之一的比例，警示比例超出 0.5–2% 時用最近的正常資料重估 τ。A4 顯示不用標籤的 τ 就夠用，所以不需要新的標註。

**限制：**
- **資料**：一季五大聯賽加兩個國際賽（2016–2018），只有事件資料，沒有球員位置。
- **危險方向是人定的**：`DANGER_SIGN` 依足球常識決定，沒有用標籤；方向定錯時，單邊會比雙邊差。
- **單邊的想法受過測試集影響**（§5.3）：R5 和 R6 完全不受影響；R6 確認了方向的效果，但沒有確認單邊勝過單一特徵。
- **15 秒是事先選的**，沒有比較其他時間窗；「失誤 → 失球」不是因果。
- **落點補值**用了之後事件的位置（§2.3）；R1 顯示這不影響結果。1,938 次退回用起點，會把傳球長度算成 0。
- **統計**：測試集只有 182 個異常，有幾個差距在 seed 間一致，但在 bootstrap 下不顯著。
- **對抗失敗沒有納入**：有些丟球權是在對抗中被搶斷，目前只算傳球失誤。

## 8. 怎麼重跑

```bash
bash setup_env.sh   # 建立虛擬環境 DM_HW2_G14、安裝 requirements.txt、下載外部測試資料（只要做一次）
bash run_all.sh     # 約 15–25 分鐘（視 CPU 而定），會自動使用 DM_HW2_G14
```

需要 **Python 3.12 以上**（`requirements.txt` 鎖定的 xgboost 3.4、numpy 2.5、scipy 1.18 都要求 3.12+；`setup_env.sh` 會優先用 3.12；本 repo 的結果是用 3.12.10 產生的，另一台電腦用 3.14.6 得到完全相同的結果）。`run_all.sh` 會依序試 `python3`、`python`、`py`，用第一個能用的；也可以自己指定：`PY=/path/to/python bash run_all.sh`。

**Windows**：用 Git Bash 執行 `bash run_all.sh` 即可（`.gitattributes` 讓 `.sh` 保持 LF 換行）。或在命令提示字元依序手動執行：

```bash
set PYTHONUTF8=1
python -u src/build_turnovers.py
python -u src/turnover_experiment.py
python -u src/ablation_analysis.py
python -u src/robustness_checks.py
```

| 步驟 | 程式 | 產出 |
|---|---|---|
| 1 | `src/build_turnovers.py` | 讀原始事件、找出傳球失誤、修正落點、算特徵和標籤 → `data/processed/turnovers.csv` |
| 2 | `src/turnover_experiment.py` | 探索、三層方法、顯著性 → `results/`（含每筆測試失誤的分數 `test_scores.csv`） |
| 3 | `src/ablation_analysis.py` | 消融、誤差分析、圖 → `results/`、`results/figures/`；沿用步驟 2 的切分、超參數與分數 |
| 4 | `src/robustness_checks.py` | 補值洩漏檢查、射門標籤、失誤後 5 秒的發展 → `results/robustness_checks.csv`、`robustness_log.json` |
| 5 | `src/statsbomb_external.py` | 外部測試（R6）：StatsBomb 英超 2015/16 → `data/processed/turnovers_statsbomb_epl_2015_16.csv`、`results/external_*`。資料由 `bash setup_env.sh` 自動下載（約 1 GB，放在 `data/external/`，不進 git；也可單獨執行 `python src/download_statsbomb.py`，不想下載就用 `SKIP_STATSBOMB=1 bash setup_env.sh`）；沒有資料時 `run_all.sh` 會自動略過 |

`src/wyscout_data.py` 是和犯規題目共用的讀取程式（同一個檔案的複本）。

**需要的原始檔**：見 `data/raw/README.md`。把 `events.zip`、`matches.zip`、`players.json`、`teams.json`、`competitions.json`、`coaches.json`、`referees.json` 放進 `data/raw/`。zip 不用先解壓縮；`data/processed/` 和 `results/` 會自動建立。
