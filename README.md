# 哪些傳球失誤會直接導致失球？
### 用 Wyscout 事件資料偵測「致命的丟失球權」

> NYCU Data Mining HW2（Anomaly Detection）
> 狀態：**試做版，主實驗完成**（2026-10-28，已修正落點缺值）。消融、誤差案例、可解釋性尚未做。所有結果可以用 `bash run_all.sh` 在 2 核 CPU 上約 10 分鐘重現
> 資料類別：**Tabular**（作業 5 類中的第 2 類），一筆資料 = 一次傳球失誤
> 姊妹專案：`hw2_foul_card`（犯規 → 吃牌）。兩者用同一份原始資料、同一種切分與評估協定

---

## 一句話說明

只用「傳球失誤當下就知道的資訊」（在哪裡丟、球落在哪裡、是否回傳、是否在對手壓迫下），判斷**這次失誤會不會在 15 秒內導致失球**。只用「沒有導致失球的失誤」訓練的 Isolation Forest 顯著優於隨機，和最好的單一特徵（球的落點）在 PR-AUC 上打平；監督式 XGBoost 顯著較好，但所有方法的絕對表現都很低。

## 1. 為什麼做這題

| 項目 | 內容 |
|---|---|
| **使用者** | 球隊的影片分析師、教練 |
| **決策** | 一場比賽約 146 次傳球失誤，平均只有約 0.45 次直接導致失球。賽後檢討時先看哪幾次？ |
| **警示之後的動作** | 把失誤排進檢討片段，找出「在哪種情況下出錯最致命」，用於訓練 |
| **審查預算** | 前 1% 與前 10% 的失誤（§5.4） |

**研究問題：**
> 只用「沒有造成失球的失誤」學出正常樣貌，能不能把致命的失誤當成異常抓出來？和犯規題目相比，結果有什麼不同？

**異常的定義（看結果之前就固定）：** 一次不準確的傳球（`Pass` 且帶 tag 1802），之後 15 秒內、同一個半場，對手進球（射門或自由球帶 tag 101，或我方烏龍球 tag 102）。

| | 例子（定義上的樣貌） |
|---|---|
| **正常** | 在對方禁區前傳中，被後衛解圍，對手往前推進，但沒有進球 |
| **異常** | 在自家禁區前被逼著回傳出錯，對手搶到球後 15 秒內進球 |

## 2. 資料

**Wyscout 公開事件資料**（Pappalardo et al. 2019，figshare），和犯規題目相同：

| 檔案 | 內容 | 用途 |
|---|---|---|
| `events_*.zip` | 3,251,294 個事件 | 傳球失誤、進球、前 10 秒情境 |
| `matches_*.json` | 1,941 場的日期、主客場 | 切分、主客場 |
| `players.json` | 3,603 名球員的位置 | 傳球者角色 |

- 賽事：英、法、德、義、西 2017/18 頂級聯賽，2016 歐洲盃，2018 世界盃
- 期間：2016-06-10 到 2018-07-15

### 2.1 一筆資料與標籤

| 項目 | 定義 |
|---|---|
| **一筆資料** | 一次 `Pass` 且帶 tag 1802（不準確）的事件，共 284,019 次 |
| **標籤** | 之後 15 秒內、同一個半場，對手進球 → 1 |
| **預測時間點** | 傳球的當下 |
| **不算丟球權** | 對抗（`Duel`）失敗。Wyscout 的對抗兩邊各記一筆，防守方被過掉也會記成「對抗失敗」，那不是丟球權 |
| **不能用** | 傳球之後的任何事件（落點補值是唯一例外，見 §2.3）；tag 2001（`dangerous_ball_lost`），標註員可能看完後續才標 |

**15 秒這個時間窗的影響**（探索階段的計數，包含對抗失敗，僅供參考）：10 秒 3,958 次、15 秒 4,976 次、30 秒 7,013 次。只算傳球失誤時，15 秒內有 869 次。

**tag 2001 不適合當標籤**：資料中有 4,028 次事件帶「危險的丟失球權」tag；其中同時是傳球失誤或對抗失敗、而且之後 15 秒內失球的，只有 299 次（其他事件類型沒有檢查）。標註員認為「危險」的丟球，大多沒有導致失球。

### 2.2 類別不平衡

| 切分 | 場次 | 失誤 | 15 秒內失球 | 比例 |
|---|---|---|---|---|
| 訓練 | 1,164 | 170,396 | 501 | 0.29% |
| 驗證 | 388 | 59,351 | 186 | 0.31% |
| 測試 | 389 | 54,272 | **182** | **0.34%** |
| 合計 | 1,941 | 284,019 | 869 | 0.31%（約 1 : 330） |

不平衡程度和信用卡詐騙相當。「全部判正常」的 accuracy 是 99.66%，所以 accuracy 不能當指標。

5,223 個進球中，有 812 個在進球前 15 秒內有對手的傳球失誤；869 次失誤對應這 812 個進球（少數進球前有多次失誤）。

### 2.3 落點缺值的修正

**問題：** 8,380 次失誤（3.0%）的傳球落點記為 **(0, 0)**，也就是剛好在我方球門線的角落。檢查原始事件後發現這是 Wyscout 沒有記錄落點時的佔位值：

| 檢查項目（世界盃 + 英超，2,016 次落點 x = 0） | 結果 |
|---|---|
| 落點剛好是 (0, 0) | 97% |
| 傳球種類 | 85% 是傳中 |
| 傳球起點 | 中位數 x = 89，91% 在對方半場 |
| 下一個事件 | 96% 是對手，多半是對手在他們自己的禁區觸球（例如 x = 4–13）或守門員出擊 |

也就是說，這些多半是**在對方禁區前傳中失敗**，球被解圍或被守門員接走，而不是傳到自家底線。

**修正（`fix_end`）：** 落點為 (0, 0) 時，用下一個事件的位置補回：
- 下一個事件是對手的：座標換回我方視角 (100 − x, 100 − y)，共 7,562 次
- 下一個事件是本隊的：直接用，共 10 次
- 沒有下一個事件、不在同一個半場、相隔超過 5 秒、或沒有座標：用傳球起點代替，共 808 次

補值後的落點 x 中位數是 88，符合「在對方禁區前丟球」。七個賽事都有這個問題（每個聯賽約 1,150–1,750 次），修正規則一致套用。

**例外說明：** 補值用到了傳球之後的下一個事件，但只取它的**位置**來補回「這次傳球本身的落點」，這個資訊原本就屬於傳球事件，只是沒被記錄。其他特徵都不使用之後的事件。

**影響：** 補值的失誤失球率只有 0.04%（全體 0.31%）。修正前，它們被當成「球掉到自家球門前」，排在單一特徵的最前面；`end_x`、`end_lateral`、`pass_len`、`backward` 都受到影響。

## 3. 特徵（28 個）

全部只用傳球當下或之前的資訊。比分、本隊累計失誤數都在記錄後才更新。

| 組 | 特徵 | 意思 |
|---|---|---|
| **原始（19 個）** | `x`、`lateral` | 丟球位置；x = 0 是自家球門，`lateral` = \|y − 50\| |
| | `end_x`、`end_lateral`、`pass_len` | 球落在哪裡、傳球長度（公尺，以 105 × 68 換算）；落點已修正（§2.3） |
| | `backward` | 落點比起點更靠近自家球門 |
| | `pt_*`（7 個） | 傳球種類：一般、高球、大腳、傳中、頭球、穿透、手拋 |
| | `minute`、`home` | 比賽分鐘、是否主場 |
| | `role_DF/MD/FW/GK` | 傳球者位置 |
| **情境（9 個）** | `dist_own_goal`、`in_own_third` | 丟球點到自家球門距離、是否在自家三分之一 |
| | `counter_attack` | 這次傳球帶有反擊 tag |
| | `score_diff`、`team_prev_losses` | 當下比分差、本隊本場之前失誤幾次 |
| | `own_events_10s`、`opp_events_10s` | 前 10 秒兩隊的動作數 |
| | `opp_duel_3s` | 前 3 秒內對手有對抗（壓迫的近似） |
| | `own_min_x_10s` | 本隊前 10 秒最靠近自家球門的位置 |

**危險特徵組（6 個，事先依足球常識定義，不看標籤）：** `dist_own_goal`、`lateral`、`end_x`、`end_lateral`、`backward`、`opp_duel_3s`。也就是在哪裡丟、球丟到哪裡、是不是回傳、是否在壓迫下。

## 4. 探索分析（只用訓練場次）

**依丟球位置：**

| 區域 | 失誤數 | 佔全部失誤 | 15 秒內失球率 |
|---|---|---|---|
| 自家三分之一 | 48,526 | 28.5% | **0.54%** |
| 中場三分之一 | 63,658 | 37.4% | 0.27% |
| 對方三分之一 | 58,212 | 34.2% | 0.11% |

自家三分之一的失誤，失球率是對方三分之一的 4.8 倍；但它佔了 28.5%，一點都不罕見。

**單一特徵可分性**（訓練集）：

| 特徵 | 方向化 AUC | KS | 致命失誤平均 | 一般失誤平均 |
|---|---|---|---|---|
| `end_x` | 0.765 | 0.398 | 43.8 | 66.4 |
| `dist_own_goal` | 0.679 | 0.261 | 43.8 | 59.5 |
| `x` | 0.670 | 0.253 | 37.5 | 52.3 |
| `own_min_x_10s` | 0.622 | 0.205 | 30.9 | 39.8 |
| `in_own_third` | 0.618 | 0.237 | 52.1% | 28.4% |
| `pass_len` | 0.614 | 0.207 | 17.5 | 24.7 |
| `score_diff` | 0.605 | 0.189 | −0.49 | −0.04 |

- **球落在哪裡比在哪裡丟更重要**：`end_x` 的 AUC 0.765，最高（修正落點前是 0.747）。
- **致命失誤的傳球比較短**（17.5 對 24.7 公尺），符合「在自家半場被逼著短傳出錯」。
- **落後時比較容易失誤後失球**（平均比分差 −0.49），可能是落後的球隊壓上、身後空檔較大。

## 5. 方法與實驗設計

### 5.1 三層方法

| 層 | 方法 | 用到的標籤 |
|---|---|---|
| **Tier 1** | (a) 全部判正常；(b) 隨機分數；(c) 單一特徵：訓練集方向化 AUC 最高的 `end_x`（越小分數越高） | (c) 只用訓練集選特徵 |
| **Tier 2** | Isolation Forest，只用訓練集**沒有導致失球**的失誤（169,895 次）訓練；`StandardScaler` 也只在這些資料上 fit。分數 s(x) = −`score_samples`(x)，越大越異常 | 訓練：不用；特徵組、超參數、τ：驗證集 |
| **Tier 2 參考** | Mahalanobis 距離（危險特徵組） | 同上 |
| **Tier 3** | XGBoost 監督式分類，28 個特徵 | 訓練集標籤 |

### 5.2 切分與防止洩漏

| 項目 | 設定 |
|---|---|
| **切分** | 依比賽日期排序：前 60% 場次訓練（到 2018-02-03）、接著 20% 驗證（到 2018-04-07）、最後 20% 測試。和犯規題目完全相同的場次切分 |
| **三層共用** | 同一份切分、同一組指標、同一批測試失誤 |
| **驗證集** | 只用來選特徵組、超參數和 τ |
| **測試集** | 最後只評估一次 |
| **落點補值** | 規則固定（§2.3），所有切分一致套用，不用標籤 |

### 5.3 超參數（只用驗證集 PR-AUC 選）

| 方法 | 搜尋範圍 | 選出 |
|---|---|---|
| Isolation Forest | 特徵組 {全部 28 個, 危險 6 個} × 樹數 {200, 500} × ψ {256, 1024, 4096} × max_features {0.5, 1.0} | **危險 6 個**、200 棵、ψ = 1024、max_features = 0.5（驗證 PR-AUC 0.0068；全部 28 個特徵的 12 組只有 0.0041–0.0050） |
| XGBoost | max_depth {3, 5} × min_child_weight {1, 10}；learning rate 0.05，早停 100 輪 | depth 5、min_child_weight 10、103 棵樹（驗證 PR-AUC 0.051） |

### 5.4 指標

| 指標 | 為什麼 |
|---|---|
| **PR-AUC**（主指標） | 隨機猜的基準是異常比例（測試集 0.0034） |
| **前 1% / 前 10% 抓到幾次** | 對應「檢討時只看 1% 或 10% 的失誤」；測試集的 1% 是 543 次、10% 是 5,427 次 |
| ROC-AUC | 輔助 |

每個方法 5 個 seed（0–4），報告平均 ± 標準差。

**顯著性：**
- 差距用**以比賽為單位的 block bootstrap**（1,000 次）算 95% CI，比較的是 5 個 seed **平均後的分數**。
- 平均後的分數比單一 seed 穩定，所以 bootstrap 表中的點估計，會和主表「5 個 seed 各自 PR-AUC 的平均」不同（§6.1 有說明）。
- Tier 2 和 Tier 3 另做 5 個 seed 的配對 t 檢定。

## 6. 結果

### 6.0 各層實際用到的樣本數

三層從**同一份原始切分**出發（依比賽日期：1,164 / 388 / 389 場），在**同一個驗證集**上調參數與 τ、在**同一個測試集**上評估。差別只在訓練時用了哪些訓練樣本：

| 層 | 方法 | 訓練：正常 | 訓練：異常（致命） | 說明 |
|---|---|---|---|---|
| Tier 1 | 全部判正常、隨機分數 | 0 | 0 | 不需要訓練 |
| Tier 1 | 單一特徵（`end_x`） | 169,895 | 501 | 只用訓練集的標籤挑特徵與方向，沒有學參數 |
| Tier 2 | Isolation Forest（全部 28 個 / 危險 6 個） | 169,895 | **0** | Normal-only：從訓練切分濾掉所有致命失誤；`StandardScaler` 也只在這些資料上 fit |
| Tier 2 參考 | Mahalanobis（危險 6 個） | 169,895 | **0** | 同上 |
| Tier 3 | XGBoost | 169,895 | 501 | 監督式，保留同一份訓練切分裡的異常樣本 |
| — | 驗證集（選特徵組、超參數、早停、τ） | 59,165 | 186 | 所有方法共用 |
| — | 測試集（只評估一次） | 54,090 | 182 | 所有方法共用 |

### 6.1 主要結果（測試集 54,272 次失誤、182 次致命）

| 方法 | PR-AUC | ROC-AUC | 前 1% 抓到 | 前 10% 抓到 | 訓練（秒） | 推論（ms / 筆） |
|---|---|---|---|---|---|---|
| T1 全部判正常 | 0.0034 | 0.500 | 0 | 11 | — | — |
| T1 隨機 | 0.0036 ± 0.0002 | 0.506 ± 0.012 | 3.0 ± 1.4 | 18.8 ± 2.5 | — | — |
| T1 單一特徵（`end_x`） | 0.0102 | **0.764** | 3 | 72 | — | — |
| T2 Isolation Forest，全部 28 個特徵 | 0.0044 ± 0.0002 | 0.572 ± 0.010 | 1.0 ± 0.6 | 30.0 ± 2.4 | 1.29 | 0.019 |
| **T2 Isolation Forest，危險 6 個（驗證集選出）** | **0.0093 ± 0.0016** | 0.606 ± 0.008 | 7.8 ± 1.7 | 47.4 ± 2.9 | 0.97 | 0.013 |
| T2 參考：Mahalanobis，危險 6 個 | 0.0052 | 0.590 | 1 | 38 | — | — |
| T3 XGBoost | **0.0315 ± 0.0009** | **0.824 ± 0.002** | **29.6 ± 2.1** | **93.8 ± 1.7** | 1.09 | 0.001 |

「全部判正常」的分數全部相同，前 1% / 10% 是依原始順序取，只是參考值。

**PR-AUC 差距**（以比賽為單位的 block bootstrap 95% CI，5 個 seed 平均後的分數）：

| 比較 | 差距 | 95% CI | 結論 |
|---|---|---|---|
| T2 − 隨機 | +0.0087 | [+0.0005, +0.0223] | 顯著 |
| T2 − 單一特徵 | +0.0023 | [−0.0045, +0.0160] | **打平** |
| T3 − T2 | +0.0190 | [+0.0049, +0.0373] | T3 顯著比較好（5 seed 配對 t 檢定 p = 4.5 × 10⁻⁶） |
| T3 − 單一特徵 | +0.0214 | [+0.0124, +0.0382] | T3 顯著比較好 |
| T2 危險 6 個 − T2 全部 28 個 | +0.0081 | [+0.0014, +0.0222] | 挑特徵顯著有幫助 |

T2 的單一 seed PR-AUC 平均是 0.0093，低於單一特徵的 0.0102；5 個 seed 的分數平均後是 0.0125，高於單一特徵。兩種算法給出相反的點估計，而 CI 都包含 0，所以結論只能是「打平」。

**怎麼解讀：**
- **Tier 2 和 Tier 1 打平，各有強項**：
  - 最前面 1% 的失誤，T2 抓到 7.8 次，單一特徵只有 3 次。
  - 放寬到前 10%，單一特徵抓到 72 次，比 T2 的 47.4 次多，ROC-AUC 也高很多（0.764 對 0.606）。
  - 這和犯規題目不同：那裡 Tier 2 在每個指標上都顯著輸給單一特徵。
- **挑特徵是必要的**：用全部 28 個特徵時，Isolation Forest 只比隨機稍好（0.0044）。
- **絕對表現都很低**：最好的 XGBoost，看前 1%（543 次）也只抓到約 30 次。致命與否大部分取決於失誤之後發生的事，失誤當下的資訊只能解釋一小部分。
- **XGBoost 的 F1 標準差很大**（0.070 ± 0.015）：異常太少，τ 在不同 seed 之間差很多，F1 不適合當主指標。

**落點修正前後的比較**（修正前的版本已覆蓋，數字取自當時的執行紀錄）：

| 方法 | 修正前 PR-AUC | 修正後 PR-AUC | 修正前前 1% | 修正後前 1% | 修正前前 10% | 修正後前 10% |
|---|---|---|---|---|---|---|
| T1 單一特徵 | 0.0080 | 0.0102 | 0 | 3 | 59 | 72 |
| T2 危險 6 個 | 0.0095 | 0.0093 | 9.6 | 7.8 | 47.6 | 47.4 |
| T3 XGBoost | 0.0323 | 0.0315 | 31.2 | 29.6 | 94.4 | 93.8 |

修正主要幫到單一特徵，因為原本被排在最前面的 (0, 0) 失誤幾乎都不致命；T2 和 T3 會同時看其他特徵，受影響很小。

### 6.2 Isolation Forest 標記了什麼（測試集，前 1%）

| 平均值 | 標記、致命 | 標記、沒失球 | 沒標記、致命 | 沒標記、沒失球 |
|---|---|---|---|---|
| 丟球位置 x | **16.9** | 41.4 | 39.8 | 53.0 |
| 落點 x | **8.9** | 16.4 | 45.0 | 67.1 |
| 回傳 | **90%** | 82.9% | 30.2% | 16.5% |
| 對手 3 秒內有對抗 | 20% | **65.1%** | 20.9% | 20.2% |
| 傳球長度（公尺） | 16.5 | 35.7 | 16.3 | 24.2 |

- **Isolation Forest 抓到的方向是對的**：被標記的失誤幾乎都是「球往自家球門方向掉」的回傳。
- **被標記但沒失球的失誤，傳球比較長**（35.7 公尺）、多在壓迫下，落點也靠近自家球門，但丟球位置在中場附近（x = 41.4），對手搶到球後離球門還有一段距離。
- **和犯規題目的關鍵差別**：在這裡，罕見的方向（回傳到自家球門附近）剛好就是危險的方向。犯規題目裡，罕見的方向（手球、已有黃牌）卻是比較不會吃牌的方向。
- **沒被標記的致命失誤**（182 次中的大多數）平均在 x = 39.8、只有 30.2% 是回傳，和一般失誤差別不大，從當下的資訊很難看出來。

## 7. 結論與限制

**目前的結論：**
1. **Isolation Forest 在這題有用，但沒有超過簡單規則。** 用事先定義的危險特徵，顯著優於隨機，和「看球落點」的單一特徵在 PR-AUC 上打平：最前面 1% 比較準，放寬到 10% 則不如單一特徵。
2. **原因是罕見與危險的方向一致。** 被標記的失誤幾乎都是往自家球門方向的回傳。這支持犯規題目得到的解釋：one-class 方法有用的前提，是異常在特徵空間裡罕見。
3. **但能預測的部分很少。** 監督式 XGBoost 的 PR-AUC 也只有 0.032。失誤會不會致命，主要取決於之後的攻防。
4. **資料清理會改變基線的結論。** 落點佔位值 (0, 0) 修正前，單一特徵在前 1% 抓到 0 次；修正後是 3 次，PR-AUC 從 0.0080 升到 0.0102。

**限制：**
- **落點補值用了下一個事件的位置**（§2.3），是唯一一個用到之後資訊的地方；808 次退回用起點，會把傳球長度算成 0。
- **15 秒是事先選的**，沒有比較其他時間窗。
- **「失誤 → 失球」不是因果**：15 秒內失球不代表是這次失誤造成的，中間可能還有其他事件。
- **沒有球員位置的追蹤資料**：失誤當下對手有幾個人在附近、守門員在哪裡，這些對結果影響很大，事件資料沒有。
- **對抗失敗沒有納入**：有些丟球權是在對抗中被搶斷，目前只算傳球失誤。
- **試做版**：作業要求的消融（至少 2 組、含一組異常偵測特有的）、誤差案例分析、可解釋性都還沒做。

**如果要正式採用這個題目，下一步：**
1. 補消融：訓練資料污染比例、分數函數、特徵組、τ 策略（和犯規題目相同的四組）。
2. 補誤差分析：至少 3 個具體案例（含 FP 與 FN）與 SHAP。
3. 試著修正 Tier 2 在前 10% 落後的問題，例如改用單邊尾端分數，只把往危險方向的罕見值算成異常。

## 8. 怎麼重跑

```bash
bash setup_env.sh   # 建立虛擬環境 DM_HW2_G14 並安裝 requirements.txt（只要做一次）
bash run_all.sh     # 約 10 分鐘（2 核 CPU），會自動使用 DM_HW2_G14
```

需要 **Python 3.12 以上**（`requirements.txt` 鎖定的 xgboost 3.4、numpy 2.5、scipy 1.18 都要求 3.12+；結果是用 Python 3.13 產生的）。`run_all.sh` 會依序試 `python3`、`python`、`py`，用第一個能用的；也可以自己指定：`PY=/path/to/python bash run_all.sh`。

**Windows**：用 Git Bash 執行 `bash run_all.sh` 即可（`.gitattributes` 讓 `.sh` 保持 LF 換行）。或在命令提示字元依序手動執行：

```bash
set PYTHONUTF8=1
python -u src/build_turnovers.py
python -u src/turnover_experiment.py
```

| 步驟 | 程式 | 產出 |
|---|---|---|
| 1 | `src/build_turnovers.py` | 讀原始事件、找出傳球失誤、修正落點、算特徵和標籤 → `data/processed/turnovers.csv`；落點補值統計印在 `results/build_log.txt` |
